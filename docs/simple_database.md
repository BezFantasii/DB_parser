# Промежуточная модель PostgreSQL

Схема содержит три таблицы вместо четырёх из сокращённого ТЗ и семи из первоначального проекта. Файл schema_simple.sql является предложением отдельной схемы, а не миграцией существующей базы. Таблицы ещё не созданы, парсер пока не подключён к ним.

## Связи

marketplaces 1 → N products 1 → N price_history.

marketplaces хранит площадки; products — карточки; price_history — наблюдения цен. Карточка Ozon и карточка Wildberries одного товара остаются двумя строками. Соответствие определяется запросом по характеристикам.

## Модели

### Marketplace

id — внутренний ID; code — уникальный код площадки; name — название. Строки создаются один раз для трёх согласованных площадок.

### Product

id — внутренний ID; marketplace_id — связь с площадкой; external_id — ID карточки на этой площадке; name и url — название и ссылка. Необязательные признаки: brand, model, connection_type, form_factor, anc, microphone, battery_hours.

Уникальность задаётся площадкой и внешним ID. NULL означает неизвестное поле; NULL у anc не означает отсутствие шумоподавления. Модель рассчитана на одну категорию — наушники. Справочники брендов и категорий не нужны для этого промежуточного этапа.

### PriceObservation

Python-модель соответствует price_history. product_id связывает наблюдение с карточкой; observed_at фиксирует момент извлечения; price — Decimal либо None; currency, region и price_kind задают контекст цены. availability, rating, reviews_count и price_text сохраняют доступные сведения.

Для одной карточки хранятся несколько наблюдений. Свежую цену выбирает представление current_prices; оно не хранит отдельную копию данных. В запросе необходимо выбрать регион, валюту и тип цены, иначе одна карточка может иметь несколько актуальных строк.

Неизвестное условие цены нельзя автоматически считать обычным; тип card пока обозначает общий класс условия, а не конкретную банковскую программу. Если появятся несколько разных условий одного класса, добавить condition_key и включить его в ключ контекста.

## Python и SQL

models_simple.py содержит обычные dataclass из стандартной библиотеки. Они дают единый формат между парсером и записью в БД, но не выполняют проверку типов автоматически и не создают таблицы.

Таблицы и ограничения создаются schema_simple.sql. Python выполняет SQL через psycopg. Изменения схемы хранятся отдельными нумерованными SQL-файлами. Модель Python и схема должны обновляться вместе.

Запись: INSERT ... ON CONFLICT обновляет карточку; затем добавляется price_history. Обе операции выполняются в одной транзакции. Уникальное ограничение наблюдения предотвращает повторный импорт с тем же observed_at и контекстом; самостоятельный новый сбор получает новое время.

## Пример параметризованного запроса

Поиск аналогов по подключению и форм-фактору с дополнительными фильтрами. Это запрос для psycopg: значения передаются отдельным словарём параметров, без строковой интерполяции.

```sql
SELECT m.name AS marketplace, p.id, p.name, p.url,
       cp.price, cp.currency, cp.price_kind, cp.observed_at
FROM products AS source
JOIN products AS p
  ON p.marketplace_id <> source.marketplace_id
 AND p.connection_type = source.connection_type
 AND p.form_factor = source.form_factor
JOIN marketplaces AS m ON m.id = p.marketplace_id
JOIN current_prices AS cp ON cp.product_id = p.id
WHERE source.id = %(source_id)s
  AND cp.region = %(region)s
  AND cp.currency = 'RUB'
  AND cp.price_kind = %(price_kind)s
  AND cp.price BETWEEN %(min_price)s AND %(max_price)s
  AND cp.observed_at >= %(freshness_cutoff)s
  AND (NOT %(require_anc)s OR p.anc IS TRUE)
  AND (NOT %(require_microphone)s OR p.microphone IS TRUE)
ORDER BY cp.price, p.id
LIMIT %(limit)s;
```

Отсутствие connection_type или form_factor у исходной карточки требует уточнения. Запрос не доказывает идентичность модели и не проверяет комплектность; он подбирает функционально похожие наушники по сохранённым признакам.

Та же схема позволяет выполнять историю цен, минимум/среднее по площадке, снижение цены через LAG, фильтры рейтинга и свежести. Запросы статусов сборов Q10 из ТЗ потребуют таблицы parse_runs: она отложена, журнал ошибок на промежуточном этапе хранится отдельно. Общие требования ТЗ этой схемой автоматически не заменяются.

## CRM и ORM

CRM — система управления клиентами, продажами и взаимодействиями. Для моделирования этой базы CRM не нужна.

Если имелась в виду ORM, это библиотека связи Python-объектов с таблицами, например SQLAlchemy или Django ORM. Для минимального проекта ORM не обязательна: dataclass, SQL и psycopg достаточно. SQL-файлы сохраняют видимую структуру запросов и упрощают демонстрацию работы с PostgreSQL.

Для ручного просмотра и выполнения SQL можно использовать pgAdmin. Он позволяет создавать и изменять таблицы, но исходником схемы должны оставаться SQL-файлы в репозитории, чтобы оба студента воспроизводили одну структуру. Не требуется писать собственную административную панель.

## Отложенные функции

Отложены справочники брендов/категорий, общий товар между площадками, история задач и обратная связь. price_history сохраняется, поскольку без неё нельзя анализировать снижение цены. Последующая parse_runs добавляется без изменения основных связей marketplace → product → price_history.
