# Какие данные нужны для доводки браузерного парсинга

Работа идёт с браузерным режимом. Backend не нужен. Скриншот ошибки помогает найти место падения интерфейса, но не показывает ответ магазина, с которым работает парсер.

## Сначала обновить и воспроизвести

1. Обновить расширение на `chrome://extensions`; папка — `E:\Baumanka\parser\JS\dist`, версия 0.3.1.
2. Перезагрузить **обе** вкладки Ozon и WB. Это нужно, чтобы content scripts и фоновый процесс были одной версии.
3. В popup выбрать «В браузере» и нажать «Сохранить».
4. Оставить обе площадки открытыми и убедиться, что вручную они показывают товары без проверки безопасности.
5. Выполнить один понятный запрос, например «худи мужское», отдельно проверить WB → Ozon и Ozon → WB.

## Минимальный набор

- Точные URL страниц поиска для обеих площадок и текст запроса. Указать, какое направление не работает.
- После ошибки открыть popup и нажать **«Скачать диагностику браузера»**. Приложить `marketplace-browser-diagnostics.json`. Для разных направлений можно скачать два отчёта.
- Указать, открывается ли этот же поиск вручную на обеих площадках, есть ли CAPTCHA, используется ли VPN/прокси и требуется ли VPN для доступа к площадкам.

Диагностика включает версию расширения и Chrome, выбранный режим, состояние текущего браузерного поиска, наличие content script на открытых вкладках, количество ссылок на товары и до 5 распознанных карточек на страницах поиска. Для WB — обнаруженные origin/path поискового API и имена параметров, без их значений. URL очищаются от посторонних параметров. Cookies, заголовки Authorization, API token, весь HTML страницы, аккаунт и страницы заказов не выгружаются. Текст поискового запроса и найденные товары в отчёте есть.

## Если нужна структура реального ответа

Если магазин возвращает HTTP 200, но карточки не распознаются, нужен **товарный фрагмент реального JSON или DOM**, а не ещё один скриншот.

Откройте DevTools (`F12`) → Network, выполните поиск вручную и найдите запрос выдачи:

- **Ozon:** обычно `composer-api` / `page/json`. Нужны status, origin/path запроса и один товарный виджет `tileGridDesktop…` или `searchResultsV2…` из `widgetStates`, с 1–2 товарами. Остальной ответ, включая `userToken`, `pageToken`, профиль и tracking, не нужен.
- **WB:** запрос выдачи с параметром `query` (обычно имя запроса `search`). Нужны status, origin/path и 1–2 элемента `products` или `data.products`. Суммы нужны в исходном виде, чтобы определить, какие поля выражены в копейках.
- **DOM:** если JSON найти сложно, в Elements выберите контейнер **одной карточки**, где есть название, текущая цена и ссылка, и скопируйте его `outerHTML`. Нужна только карточка, не вся страница.

Не присылайте `Copy as cURL`, cookies, пароль, Authorization, API token или полный необработанный HAR. Ответы магазинов могут содержать токены: нужен только товарный фрагмент, который можно просмотреть перед отправкой.

## Как будет проверяться исправление

Сначала ответ из вашего Chrome станет тестовым примером для соответствующего парсера. Затем проверяются оба направления, текущая и зачёркнутая цены, ссылки, смена запроса и отсутствие переключений/навигации. После этого потребуется повторная проверка в вашем обычном Chrome: тестовый Chromium может получать другой ответ или 403.

Если площадка отвечает 403, это отдельный вопрос доступа, а не ошибка разбора JSON. Гарантировать постоянный доступ при меняющейся антибот-защите нельзя; задача — подтвердить корректную работу с доступными браузерными сессиями и реальными ответами обеих площадок.
